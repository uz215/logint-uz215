### 0.3 修改同步规则（强制）
任何功能修改必须做到"**四同步**"：
1. **代码**：改实现并保持"单一裁决/单一来源"（结论只在 `arbiter` 一处确定）；
2. **配置**：参数/阈值外置到 `logint.json` 或井 `info.json`，写清默认值与单位；
3. **测试**：更新/新增对应自检（单元、契约、报告黄金、验收/回归至少跑一项）；
4. **文档**：更新本手册对应章节 + §12 变更记录；重大流程变化同时更新 `docs/系统架构与产品路线.md`；每次改动在《P0执行记录》追加一轮记录。

提交信息格式建议：`<type>(<module>): <动作/原因>；验证：<测试/指标>；文档：<章节>`。  
**禁止**只改代码不改文档；**禁止**新增独立程序/入口（所有能力作为既有程序的功能）。

## 1. 系统流程与数据契约

### 1.1 主流程（logInt.run_workflow）
```
LAS/DLIS 加载 → 单位/非法值/深度清洗 → QC
→ VSH/孔隙度/饱和度/矿物反演（按剖面类型）
→ 岩性识别（规则 + 元素矿物 + ML + 区域约束）
→ 流体规则解释（截止值/分带/干层/气测图版）
→ 分带/油气同层拆分/重力分异整饰
→ 唯一裁决 arbiter（rules/ML/auto，见 info「解释来源」）
→ 后处理：解释井段裁剪、气田先验、Sg/So、不确定性复核、录井图气测证据、地层顶
→ canonical 层表/CSV/LAS → 可视化（quicklook/综合图/交汇图）
→ 决策记录 + 完整报告（HTML/PDF）→ 运行清单/运行状态
```

## 2. 数据加载、清洗与 QC

### 2.1 实现
- 加载：`logInt.py` 中 `DataLoader`（LAS/DLIS/CSV；曲线别名 `CURVE_NAME_ALIASES`）；
- 清洗：`logsys/clean.py`（`clean_well` 一次完成）；
- QC：`DataLoader.data_quality_check()`，输出 QC 报告；清洗与 QC 通过链接项 `data_cleaning` 关联。

### 2.2 方法（clean.py）
1. **单位归一**：NPHI 小数→%；RHOB kg/m³→g/cc；DT us/m→us/ft（按列名/量级判断，记录到报告）；**CAL/BS 单位恒为 in，不做 cm/mm 换算**；
2. **非法值清洗**：物理范围裁剪/置空（GR、RT、DEN、CNL、DT、POR、SW 等）；识别 `-999/-9999/ICV/IHV` 等哨兵；
3. **深度清洗**：去重、排序、空深度剔除；
4. **厂家退化结果隔离**：POR 中位≤0.02 或 SW 中位≥95%、且有效占比≥70%、有原始曲线 → 原列重命名 `*_VENDOR`，由程序重算（RP-13 案例：SW 100→0.14–0.19）；
5. **LAS 注释/参数语义识别（2026-11-02）**：曲线名不认识时，从 `~C` 描述与 `~P TLFamily_*` 语义识别：
   - `Gamma Ray` → **GR**（语义优先级：注释明确 `gamma ray` 且名称 `GR_EDTC/GRN`（归一化伽马）优先；`GREV/Gamma EVR` 仅兜底；排除 Gamma 能谱 `GRSPEC`）；
   - `Caliper` → **CAL**（仅真井径名/描述：CALI/HCAL/CALA/CALIPER；须通过物理范围校验：中位 2–30in、95%<60in）；
     **`CALC1/CALC3/CALC5` 不是井径**——是岩性酸解 CO2 量：`CALC1`=前1分钟 CO2（此阶段白云岩不反应）→ **灰岩指示**；`CALC3/CALC5`=第3–5分钟 CO2（灰岩已反应完，白云岩与盐酸反应）→ **白云岩指示**；禁止当 CAL，也不能把三条统称灰岩含量；
   - `BS/BS1..BSn` 参数（单位 in）→ 合成 **BS**（按用户口径取最后一个/最小 bit size，如 8½"）；
   - 实现：`logInt.parse_las_semantics_raw()` + `standardize_curve_names(descriptions=..., bit_sizes=...)`；
   - 案例：CuraCao-1 `LQC.las` → GR_EDTC(Gamma Ray)、BS=8.5in；**LAS 无真井径**（CALC1=灰岩酸解CO2、CALC3/5=白云岩酸解CO2，已正确排除）；
   - **DLIS 同样支持**：通道 `long_name/units`（如 `CALA/Caliper`、`GREV/Gamma EVR`、`BITSIZE/Bit Size`）与参数 bit size 走同一 `standardize_curve_names`；
     dlisio 1.x 入口为 `from dlisio import dlis; dlis.load()`；
6. **输出报告**：行数、单位修正、非法值计数、隔离列 → `<井>_data_clean_report.json`。

### 2.3 QC
- 检查项：深度单调/重复、必需曲线、值域、曲线有效性、数据充分性联动；
- 评分/等级：`quality_level`（GOOD/FAIR/POOR 等）、`overall_score`；QC 报告 `<井>_qc_report.json`；
- 充分性门禁（`logsys/sufficiency.py`）：核心曲线覆盖率 ≥80% OK、≥50% DEGRADED、<50% INSUFFICIENT（RP-13 实测 12%→INSUFFICIENT，结论仅供参考）。

### 2.4 修改点与坑
- 改单位/别名：`CURVE_NAME_ALIASES`、`normalize_units`；改完必须跑 `logsys.test_clean` + 至少一口实井；
- 厂家列隔离误伤：核对"有效占比"而不是全序列占比；
- `IS_CASING` 可能含 NaN → 布尔掩码前必须 NaN→False；
- processed 数据个别 MD=NaN 行：出图/出图版前需 dropna 取有效深度（已修复 logvis）。

## 3. 岩性识别

### 3.1 实现
- 规则/证据：`logInt.py` 岩性识别（GR/VSH/PE/DEN/CNL/DT、元素矿物VOL_*、岩性证据）；
- ML：`logsys/lithcal.py`（训练/交叉验证）、`logsys/pipeline_lith.py`（主流程应用）；
- 区域约束：`logsys/region_lith.py` + `logsys/knowledge/region_lithology.json`；
- 真值/评估：`logsys/truth_lith.py`、`logsys/lith_validate.py`。

### 3.2 方法
1. **规则识别**：按剖面类型（sand_shale/carbonate/evaporite_igneous/mixed）选矿物组合与判据；无判据命中时**默认 unknown**（禁止默认泥岩）；低分兜底：GR≥110/VSH≥0.55→shale、GR≤75/VSH≤0.20→sandstone，否则 unknown；
2. **元素测井矿物**：VOL_CALCITE/VOL_DOLOM/VOL_ANHY/VOL_BASALT/VOL_SALT/VOL_ILLITE 等覆盖>50% 时作为岩性/真值来源；
3. **ML**：特征基础曲线 + 滚动统计（M11/S11/M31），ExtraTrees(500, leaf=2)，5 折分块 CV；应用时平滑窗 11 + 区域约束；
4. **区域约束**：只约束 unknown（不硬改已识别点），记录证据；
5. **真值来源分级**（truth_lith）：岩石分析 0.95/±1m > 元素矿物 0.90/±2m > 录井图结构化 0.80/±3–5m（≤10m）> 录井图 PDF 0.75；
6. **评估**：`lith_validate` 输出准确率、macro-F1、precision/recall、混淆矩阵，及 accuracy_large(≥2m)/accuracy_thin(<2m)、最佳深度平移（±10m）。

### 3.2b 岩性/剖面判定优先级（2026-11-02 用户定案｜规范 LITH-2026-11-02-v2.2）

1. **元素测井第一**（规范 §0 LITH-2026-11-02-03）：Quanti.Elan `CALCITE_QE/DOLOMITE_QE/SHALE_QE/QUARTZ_QE` 等先映射为 `VOL_CALCITE/VOL_DOLOM/VOL_ILLITE/VOL_QUARTZ`；元素矿物体积可直接定岩性/剖面，`VOL_ILLITE` 还用 KTH/GR 回归外推到全井（火成岩段除外）→ `VSH_ELEM`。
2. **曲线特征值第二**（LITH-2026-11-02-02）：密度、声波、中子、电阻率的高低（本井/本段分位）用于补充/交叉验证；不再用固定绝对值做否决。
3. **GR 只作井内分位位置**（LITH-2026-11-02-02）：GR 绝对值不能作为任何岩性的否决条件；`GR_lime_max/GR_dol_max/GR_sand_max/GR_shale_min` 由本井分位/直方图自动确定；高 GR 的泥质碳酸盐岩不得因 GR=87/110 被否决。
4. **单一仲裁**（LITH-2026-11-02-06）：元素剖面 > 交汇图/PTI/密度覆盖 > 点级岩性计数；后者只能参考，不能反向覆盖元素结论；旧 `<井>_lithprofile.json` 仅在同井名、标准标签、长度一致时复用，`Unknown` 缓存禁用。

### 3.3 关键数据/配置

- 真值：Trakes `岩性解释剖面.xlsx`、111D `*_mineral_lith_truth.csv`、录井图 PDF（masterlog 解析）；

### 3.4b 岩心/XRD/XRF 标定（2026-11-02 用户定案）

- **数据源**：井目录下 `*井数据*.xlsx` 的 `SWC Lithology` / `SWC&Core Final` / `XRD` / `XRF` / `lithall` 表，以及 `Coredata.txt`；不用录井图也能标定。
- **深度基准（用户 2026-11-02 定案）**：井壁取芯/岩心是**测井深度**，直接按 0.30m nearest 挂 `CORE_LITH/CORE_PHIE`；XRD/XRF 是**录井深度**，与测井深度差几米（正常 3–5m，上限 10m），必须做**逐样本滑动窗+局部锚点**深度配准（换钻具/起下钻都可能变，不是全井固定值，也不是固定分段），再挂 `XRD_*/XRF_*`；
- **读取/挂接**：`logsys/core_calib.py` 按上述基准挂接；XRD/XRF 用方解石/白云石/石英与 `CALCITE_QE/DOLOMITE_QE/QUARTZ_QE` 相关最大处估偏移（本井实测 **−4.75m**）；无资料自动跳过。
- **优先级**：岩心岩性 > 元素矿物 > 曲线特征；`apply_core_lithology()` 在**分层表生成前**用 `CORE_LITH` 覆盖 `LITHOLOGY`/`LITHOLOGY_MC`，`LITH_MC_CONF=9`，并留痕“岩心标定”。
- **本井实测**：1-SPS-108 可挂接 283 个岩心点（XRD 104、岩心孔隙度 237）；最终点级岩性与岩心 **100% 一致**；分层表 140 层（limestone 76 / dolomite 60 / sandstone 3 / anhydrite 1）。
- **酸解 CO2 曲线**：`CALC1→CALC_LIME_CO2`（灰岩指示），`CALC3/5→CALC_DOL_CO2`（白云岩指示），并派生 `CALC_LIME_RATIO/CALC_DOL_RATIO`；原始 CALC1/3/5 保留、不参与 CAL 井径；
- **XRD 交叉检查**：XRD_CAL 与 `CALCITE_QE` 均值 0.286 vs 0.352，相关 0.57；XRD_DOL 均值 0.272 vs `DOLOMITE_QE` 0.166，说明元素反演会低估白云石——因此岩心点必须硬标定，层间再用元素/曲线外推。

## 4. 测井解释（油气水）

### 4.1 规则解释
- 实现：`logInt.py`（`build_interpretation_rules`/解释段）；
- 截止值：`por_hc`、`por_dry_max`、`sw_hc`、`sw_deny`、`rt_gas`、`rt_oil`、`rt_water`、`por_gas_min`（气/油孔隙度下限）；
- 结论：GAS / GAS_OIL / OIL / OIL_WATER / WATER / DRY / NonReservoir；
- 分带：区域流体分带（如 BET-1 ft、111D m、RP-13 自动井段+气田先验）可在 `info.json 区域知识`/`区域标定`；
- 干层：低孔低渗+不可采，**不是不含油气**（Sg/So 仍计算，见 §4.7）；干层数量需受控（不能太多）。

### 4.2 气测图版（C1–C5）
- 实现：`logsys/gasplate/`（`engine.evaluate_points/evaluate_layers/fuse_with_log`；`methods`：Pixler 比值、C1/重烃、C2/C3、3H、气体评价）；
- 规则：气/油由**图版决定**，REG 仅作证据；图版无依据时保留测井结论并标 `GAS_REVIEW`，禁止强制降油；
- 干气补充（孟加拉干气）：C1/C2>50 且 C2/C3<1 或 C3≈0 → GAS；
- 输出：`PLATE_FLUID/PLATE_CONF/PLATE_WHY`。

### 4.3 ML 解释
- 实现：`logsys/wellcal.py`（fit/apply，RF/DT，5 折 CV，特征 GR/PHI/SW_COMP/SW_LOG/LOG_RT/VSH）、`logsys/pipeline_ml.py`（主流程）；
- 模型：`data/calibration/models/<井>.joblib/.json`；CV 写入 meta；
- 重要：数据清洗/曲线口径变化后**旧模型会失配**（Trakes 实例：清洗前模型→16.5%；按井重训→97.2%）；改清洗/曲线后必须重训并复跑验收。

### 4.4 唯一裁决（arbiter）
- `logsys/arbiter.py`：读 `info「解释来源」`（rules/ML/auto）；auto 时按模型 CV（≥0.80 用 ML）选择；候选 rules/ML → canonical + `_interpretation_decision.json`；
- 点级 INTERPRETATION 与层表同源；单一来源，禁止多处改结论。

### 4.5 后处理（统一入口）
- 分带/油气同层拆分：`zonation.py`、`mixed_split.py`；
- 重力分异：`enforce_fluid_segregation`（气上/油中/水下；GAS_OIL 气在上）；
- 解释井段裁剪（自动=裸眼+电测覆盖；info 优先）；
- 气田先验（邻井试油均气井）：OIL/GAS_OIL→GAS（点级+层表同步）；
- 录井图气测异常证据：`MASTERLOG_GAS` 标记，不强制改判；
- 地层顶（设计）→ `FORMATION` 列；
- 不确定性复核清单：薄层/气测异常非气/图版冲突 → `UNCERTAIN` + `<井>_review_list.csv`。
- **砂体一致性回填（R68，用户定案）**：`enforce_fluid_segregation` 入口。根因=统一储层过滤（VSH>0.40/POR<截止）把同一砂体中下部留空，流动单元被切成"顶部薄水层+以下空白"（XIMENIA-5 51 号层 1853.7–1861.7m 即此例）；用户口径"水不能在上部、同一层砂岩不该分两层"。规则=同一连续**储层岩性体**内留空点随**向上就近**的已解释点结论回填（下部随上部，天然排除水在油上），不跨泥岩隔层、不另立结论；闸门=总孔隙度 `PHI>=0.06`（真致密才算隔段，有效孔隙度 POR 受泥质校正归零≠致密）；回填为油气时受 `Sw>0.85`/`RT<1.0` 物理下限否决（R58 同口径）；回填后重算 `is_res` 流动单元资格，顺序仍归重力分异整饰统管。实测 XIMENIA-5：回填 229 点，51 号层并为 1852.6–1865.8m 连续 OIL，13/14 号层间隔 639.8–642.9m 并入 625.0–647.4m 同层（61 层）。
- **解释底界（R68，用户定案）**：位置=两个解释引擎（高级/规则）之后、按层聚合之前，一处生效。判据=列级择优：按 `POR/POR_EFF` > `PORD/PHI` 优先级取第一个存在有效正值的孔隙度列（不做跨列并集 —— 深部 RHOB 死值会让 PORD/PHI 饱和在 0.4 上限），与 Sw 同时有效的最深点为止；以下 `INTERPRETATION`/`ITP`/`*_SCORE`/`HIT_RATE` 清空。用户口径"2830 米以下没有有效曲线就别解释了"。实测 XIMENIA-5：底界 2827.8m、217 点留空（原 2832–2840m OIL 属伪结论，已消失）。

### 4.6 层表
- `logsys/layers.py::build_layers`：最小层厚、薄层吸收（同族才合并，不跨族）、`THIN/BELOW_MIN_THICK` 标志；
- 字段：TOP_MD/BASE_MD/THICKNESS/LITHOLOGY/INTERPRETATION/GR_MEAN/VSH_MEAN/PHI_MEAN/SW_MEAN/RT_MEAN/SG_MEAN/SO_MEAN/SWE_MEAN/REVIEW_FLAG 等。

### 4.7 Sg/So 与守恒（用户定案）
- `logsys/fluids.py::compute_sg_so`：
  - GAS：Sg=1−Sw；OIL：So=1−Sw；
  - **GAS_OIL=油气同层（测试油气同出、比例大体相当）：默认 Sg/So 各半**；如实际测试比例不同，可在 `info 解释参数.气油比例` 指定（0.4=气占40% 仅示例，不是固定规则）；**不用气测组分自动推断饱和度比例**；
  - **干层 DRY 仍含烃**：按 1−Sw 计算并按图版/比例分配（物性差/不可采 ≠ 无油气）；
  - 守恒：`SW_EFF = 1−SG−SO`，SG+SO+SW_EFF=1（Sw 实测保留）。

| `decimate` | 包络降采样（min/max 包络，**保留薄层尖峰**）、深度窗口切片 |
| `datasource` | 井数据装配：解释曲线集 `processed.csv` / 层段表 / 井 `info.json` |
| `catalog` | 曲线目录（复用 `project_model.classify_variable` 的三色语义） |
| `header` | 图头字段：分组井信息展平 → 可编辑清单 → 写回（保持分组结构） |
| `canvas` | 交互画布（matplotlib Qt5Agg / `FigureCanvasQTAgg`，R83）：多道共享深度轴、缩放/平移/框选、游标读值 |
| `window` | 主窗口三栏（PyQt5 `QMainWindow`，R83）：曲线目录（Qt 原生拖拽源）｜画布｜道与曲线·图头·读值 |

**为什么合并**：绘图模块统一叫 `logvis`——静态交付图与交互图同一文件、同一套 import、同一份符号表，避免两处版式/图头逻辑分叉；原包删除后仅保留 `logsys/test_logview.py` 自检。

**交互约定**：
- 滚轮=以光标深度为锚点缩放；左键拖拽=平移；右键拖拽=框选放大；中键/双击=复位全井；
- 鼠标移动=跨道深度游标 + 实时读值（右侧「深度读值」页签）；
- **曲线拖入绘图区即自动绘图**：落到哪道就画进哪道（双击=加到当前选中道）；
- 「道与曲线」页签可删曲线/删道/调道序；「图头」页签改字段即写回 `info.json`；
- 版式可一键切「快速图版式 / 综合图版式」；布局可存 `<井>logvis.json`。

**「与快速图/综合图结合」的三条通路**：
1. **版式同源**：交互画布与静态出图共用 `resolve_track_layout`；模板 `track.layout` 是唯一源头，
   代码里的 `FALLBACK_LAYOUT` 仅作兜底（数值与原硬编码逐一对齐）。
   改 `templates/*.json` 的 `track.layout` → 交互画布与甲方交付图**同时**变，道序道宽永远一致。
2. **图头同源**：改的是同一份 `<井>info.json`——`logvis._load_well_info_json` 每次出图重读，
   所以交互画布里改的图头，**后续快速图/综合图出图同步生效**。
3. **曲线同源**：交互画布读的就是解释曲线集 `processed.csv`（与静态出图同一份数据），
   合并后直接复用同文件的 `draw_lithology_pattern` 与 `FLUID_COLOR`——两处版式天然一致。

**二维数据（R82）**：一维道是「深度 × 单值」，二维道是「深度 × bin/采样」的强度矩阵
（伪彩图），两者共用深度轴但 x 轴语义不同，因此分开容器、分开目录条目：

| 数据类型 | 来源 | 装配方式 |
|---|---|---|
| 核磁 T2 谱（64 bin） | `processed.csv` 的 `T2_DIST[0..63]` | 折叠为单个 `ArrayData`，T2 轴 0.3–3000 ms 对数分布 |
| 核磁 T2 谱（区间） | `*_nmr_results_*.csv` 的 7 个区间列 | 区间中值作轴，直接组装 |
| 核磁 T2_DIST / T2W | CMR / MRIL DLIS 的 2D 通道 | `dlis_tool._load_logical_files` 独立只读，不走一维帧解析 |
| 声波波形 / 回波串 | DLIS 的 `DWF*` / `ECHO_*` / `WF_*` 2D 通道 | x 轴为采样序号，symmetric 色标；>400 万元素按「保峰值」降采样 |

- **目录折叠**：64 个 `T2_DIST[i]` 不再冒充 64 条一维曲线，折叠为一条「核磁二维谱」条目
  （1-SPS-108 目录从 325 → 262 条）；二维条目拖入绘图区即建二维道，`set_array` 与
  `set_curve` 互斥（轴语义不同）。
- **深度基准对齐**：不同测次（LWD 随钻 MD 与电缆 MD 单位不同）的二维数组在装配阶段
  按首尾线性映射到主井深度（`_align_arrays_to_depth`），并写入 `note` 标注；
  拖入时**不改**全局深度窗口（否则所有一维道跟着错位）。
- **渲染**：`pcolormesh` + `LogNorm`（核磁正值）/ `Normalize(-lim, lim)`（波形）/ 线性三种色标；
  NaN/Inf/非正值统一掩码，98 百分位截尾防脏数据溢出（nmr_results 有 1e293 级异常值与负值）。
- **游标读值**：二维道额外显示当前深度行的峰值 bin/采样位置与强度（`·峰值bin` / `·峰值`）。
- **静态出图零影响**：二维道只在交互画布存在，`FALLBACK_LAYOUT` 与模板 `track.layout`
  不变；golden qlpt/cmpt 逐像素不变。

**踩过的坑**：
- 【R83】GUI 统一由 tkinter 迁到 PyQt5：画布用 `FigureCanvasQTAgg`（matplotlib 3.11 的
  `backend_qtagg`，`FigureCanvasTkAgg` 退出）；曲线拖入改用 Qt 原生 DnD（目录树项携带
  `application/x-logvis-curve` mime，画布 `dragEnterEvent/dropEvent` 按 `QWidget` 像素反查落点），
  比原来的三段式自实现更稳。全进程唯一 `QApplication` 由 `logsys/qtgui.get_app()` 管理；
  对话框统一走 `qtgui.*`，`QTreeWidget` 等 iid 语义由 `logsys/qtcompat.py` 适配。
- 电阻率族动态范围 0.2–2000 ohm.m，**线性轴会把曲线压成一条平线** → 电阻率族默认对数刻度。
- 尖峰必须用 min/max 包络抽稀，均值抽稀会抹平薄层响应。
- 抽稀后要按**画布像素高度**决定档数（`pixel_height × 0.75`），否则缩放后要么卡要么糊。

### 6.1 程序定位与文件

### 6.2 方法库（gasplate）

#### 7.5.1 沿革：LFS 2GiB 上限与压缩存储（2026-11-13，R79 后已停用，仅留档）
> 本节记录一次已完成的工程攻坚，**当前不再作为入库方案**：2026-11-13 曾用 gzip+LFS 把 2.37GB
> 的 `kb.db` 压到 476MB（18.7%）并成功推送；随后按合规要求取消入库（`git rm --cached`），
> `.gitattributes` 中的 `gzip-lfs` 规则与本机过滤器配置随之移除/失效。
> 保留此节以便日后若确需入库，能直接复用结论。

GitHub LFS **单对象硬上限 2GiB**（`Size must be less than or equal to 2147483648`，HTTP 422）。
知识库扩充到 2.37GB 后直接推送被拒。实测 FTS5 索引净占 **1.31GB**（去掉 FTS 后全库仅 1.05GB），
但 FTS 是检索索引不可丢弃；`VACUUM`+FTS `optimize` 仅回收 0.4%（无膨胀可回收）。

当时的处置：**gzip 压缩后再入 LFS**，工作区文件仍是可直接打开的 SQLite：
- `.gitattributes`：`data/kb/kb.db filter=gzip-lfs diff=lfs merge=lfs -text`
- 每台机器需配置过滤器（与 `git lfs install` 同批，一次性）：
  ```bash
  git config filter.gzip-lfs.clean  "gzip -n -c | git lfs clean -- %f"
  git config filter.gzip-lfs.smudge "git lfs smudge -- %f | gunzip"
  git config filter.gzip-lfs.required true
  ```
- 实测 2,541,371,392 B → 476,378,362 B（**18.7%**），远低于 2GiB 上限，且留有约 4 倍增长余量。
- 注意：① 压缩产物由 `gzip` 命令生成，与 Python `gzip.compress` 字节不同 → 生成指针必须走
  过滤器真实链路（`git add data/kb/kb.db`），不可手工构造，否则工作区恒为 modified；
  ② 提交历史里若残留未压缩的大对象指针，推送仍会失败（需重写该提交）；
  ③ 勿用 `git lfs checkout`（会绕过过滤器，把压缩内容写成 kb.db）。

更新流程（R79 现行）：
```bash
python -m logsys.knowledge.build            # 重建/增量 → 本地 data/kb/kb.db
# 更新 data/kb/kb_manifest.json（统计/sha256/时间）→ 入库
git add data/kb/kb_manifest.json
git commit -m "chore(kb): 更新知识库统计 <统计>"
# kb.db 本身不入库；需要分发时用备份介质（gzip 压缩件约 455MB）单独传递
```

#### 7.5.2 合规台账：远端历史残留与清除预案（2026-11-13 决策）

**现状**：`kb.db` 已取消跟踪（提交 `61409eb`），新提交不再携带知识库。但**远端历史仍留有旧版指针**，
任何人都可以 checkout 旧提交并从 LFS 下载：

| 来源提交 | LFS 对象 | 内容 | 体量 |
|---|---|---|---|
| `9dcc193`（2026-11-02，kb.db 纳入 git） | 原版指针 | 初版知识库 | 约 111MB |
| `34098f2`（2026-11-13，logknow 线扩充） | gzip 指针 | 扩充后知识库（gzip 18.7%） | 476,378,362 B |
| 涉及提交共 8 个 | `9dcc193`、`45a1e1a`、`5374bff`、`dc89ee6`、`3e5dfe0`、`34098f2`、`31dee3d`、`61409eb` | | |

**决策（2026-11-13，用户确认）**：**保持现状，不重写历史**。理由：
1. 重写会改写 `main` 全线提交 hash → 另一台机器必须 `git fetch && git reset --hard origin/main`，否则分叉；
2. 强推属不可逆操作，而「知识库不再外流」这一目标已由「不再入库」达成；
3. GitHub LFS **存储端的字节无用户侧删除接口**，历史重写后仍需平台回收或提 support 请求，
   重写并不能保证字节立即消失 —— 收益有限、风险明确。

**将来若需彻底清除**（届时执行，注意上述代价）：
```bash
# 1) 净化历史：移除所有提交中的 data/kb/kb.db（filter-branch 只重写受影响提交及其后代）
git filter-branch --force --index-filter \
  'git rm --cached --ignore-unmatch data/kb/kb.db' \
  --prune-empty --tag-name-filter cat -- --all
# 2) 清本地 LFS 缓存（远端对象不动）
git lfs prune
# 3) 强推（不可逆；另一台机器须 fetch + reset --hard origin/main）
git push --force origin main
# 4) GitHub LFS 存储端残留字节 → 提 support 请求删除
```

**其余数据资产处置（2026-11-13 用户确认，暂时保留）**：

- `data/kb/well_knowledge/`（井级知识文本，含 1-SPS-108 井位/坐标/录井/气测）—— 保留；
