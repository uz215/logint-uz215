## 一、动机：为什么要在 logInt 里做"项目-井"界面

上一轮对 Techlog 2019.2.1 主安装包（990 MB MSI）的静态取证给出了完整的功能地图，其中**最能体现其架构意图**的是 Project Browser 的对象模型：

> "What is a well, dataset and variable" —— Techlog 的数据组织不是"文件树"，而是
> **Well → Dataset → Variable** 三级对象模型，每个 Variable 带 **family**（族）决定
> 显示方式与插值策略，每个 Dataset 带**类型**（连续曲线集 / 顶底边界层集 / 点集 /
> 成果集 / 图像集）。

而当前 logInt 的形态是**单井工作流**：

| 维度 | logInt 现状 | Techlog 范式 |
|---|---|---|
| 启动方式 | 选一个井目录 → 跑解释 → 出图 | 打开项目 → 浏览多井 → 钻取到变量 |
| 数据组织 | 目录即井，文件即产物 | Well / Dataset / Variable 三级对象 |
| 多井视图 | 无（需人工逐口处理） | 项目树 + 过滤 + 分组 + 条件选择 |
| 状态可见性 | 无（只有 run_manifest 散落各目录） | 井状态图标 + 属性面板 + 实时汇总 |

本次工作把 Techlog 的**项目浏览器范式**移植到 logInt 的 tkinter 技术栈上，
形成 `Project → Well → Dataset → Variable` 四层树 + 属性面板 + 输出区的标准 IDE 布局。

**注意边界**：本次交付的是**浏览/导航/管理层**，不改动任何解释逻辑、阈值与出图口径。
Techlog 的 Workflow Engine、AWI、Ocean 插件机制等更重的机制不在本次范围。

## 二之二、第二轮定案：项目在前，QuickLook 在项目里做

### 2.2.1 为什么要改

第一轮做完后，**QuickLook 仍是启动界面里与"项目浏览器"并列的顶层任务**。
用户指出："应该是 project 在前，quicklook 在 project 里做"。这个纠正背后有
三条硬理由，都不是排版偏好：

| 理由 | 具体事实 |
|---|---|
| **作业需要"源"，项目才能同时提供"源"与"产物"** | 项目树扫的是产物目录 `output/<井名>/`；QuickLook 需要的是**原始井目录**（原始 LAS + 地质设计 + 录井图 + 甲方格式），如 `D:\360\Indonesia\BET-1`。两者是不同目录、不同命名（井 `RASHIDPUR_13` 的资料目录叫 `RP-13`）。只有"项目"这一个对象能同时挂住两者。 |
| **产物必须落回项目树** | logInt 内部用 `Path('output')/井名` 定位产物（相对 CWD）。在项目里跑作业 → 产物直接落回 `output/<井名>/` → 刷新项目树即可看到新数据集。作业与产物形成闭环，而不是散落在别处。 |
| **批量是项目级能力** | "一批井依次出快速解释图"这件事，在单井工作流里根本没有对应物。它只有在项目语境下才成立。 |

### 2.2.2 落地后的入口层级

```
logInt 启动
  └─ 统一启动界面
       ├─ 【项目】（默认，第一项）──→ 项目浏览器
       │     └─ 项目树 Project → Well → Dataset → Variable
       │          └─ 右键井 → 快速解释图（Quick Look）   ← 作业在这里
       │          └─ 右键井 → 综合解释
       │          └─ 工具条 → 批量快速解释图 / 批量综合解释（待解释井）
       └─ 【单井综合解释】─────────→ 原有单井通道（保留，无项目时的快捷入口）
```

顶层不再并列"quicklook 快速解释图"任务 —— 它已成为**项目内的井级作业**。

### 2.2.3 井 ↔ 原始资料目录的关联

作业要能跑起来，必须知道每口井的原始资料在哪。这个映射**不能靠文件名猜**
（`RASHIDPUR_13` ↔ `RP-13`），所以采用 Techlog 的做法：**显式存下来**。

- 配置文件：`<项目根>/project.json`（原子写入）
  ```json
  {
    "version": 1,
    "source_roots": ["D:\\360\\Indonesia", "D:\\360\\Bangladesh"],
    "wells": {"RASHIDPUR_13": {"source_dir": "D:\\360\\Bangladesh\\RP-13"}}
  }
  ```
- 解析优先级：**显式绑定** > **自动探测** > 空
- 自动探测四级策略：同名子目录 → 归一化宽松匹配（`Trakes KE-1` ↔ `TrakesKE-1`）
  → 含该井 LAS 的子目录 → 源根散文件（TITAS-31 的 LAS 就在 `Bangladesh/` 根部）
- 防误配：归一化后较短一方须 ≥4 字符，否则短名井（`3`、`1`）会误匹配到 `3-SPS-111D`

### 2.2.4 作业执行器（为什么用子进程）

logInt 的解释流程是重量级的（读 LAS → QC → 岩性 → 沉积相 → 解释 → 出图），
单井常需数分钟；且它会改写全局状态（`_PLOT_MODE`、`config['output_dir']`、
matplotlib rcParams）。因此作业在**独立子进程**中执行：

| 设计点 | 做法 | 原因 |
|---|---|---|
| 隔离 | `subprocess.Popen` 起独立 `logInt.py` | 全局状态不污染 GUI；崩溃不影响浏览器 |
| 解释器 | **优先 `<repo>/.venv/Scripts/python.exe`** | GUI 可能由别的 Python 启动，而依赖装在项目 venv 里；用 `sys.executable` 会因缺 numpy/pandas 而失败 |
| 非交互 | `LOGINT_NONINTERACTIVE=1` + `stdin=DEVNULL` | logInt 依赖检查里的 `input()` 在无 stdin 时会抛 EOFError 直接终止作业 |
| 落盘 | 子进程 CWD = **项目根的父目录** | `Path('output')/井名` 相对 CWD → 产物正好落回项目树 |
| 实时日志 | 逐行读 stdout → 队列 → GUI 线程写 Output window | 对应 Techlog 的 Output window，且不跨线程操作 tk |
| 甲方格式 | 自动取井目录内 `*_qlpt.json` | 井的甲方图版随井而异 |

### 2.2.5 状态语义修正（第一轮遗留的缺陷）

第一轮把"有源无产物"标成 `no_source`「缺原始资料」—— **判据与标签相反**。
第二轮拆成两个**正交维度**：

| 维度 | 取值 | 含义 |
|---|---|---|
| `status`（产物完成度） | 已解释 / 部分完成 / 待解释 / 仅建目录 | 产物跑到哪一步了 |
| `has_source`（源关联） | 已关联 / 缺源 | 能否在项目里重跑或做 QuickLook |

混成一个维度会让正常井被误标为红色错误，因此拆开。树节点上未关联源的井
带 `⚠` 标记，属性面板分行显示。

## 二之三、第三轮定案：两个前置界面合并进项目工作台

> 用户指令：「把前 2 个界面都整合到这个界面里，启动后就在这个界面里工作」

### 2.3.1 改的是什么

第二轮之后，logInt 的界面序列仍是：

```
logInt 启动
  └─ 界面①：统一启动界面（选任务 + 选井目录 + 校正 LAS/气测/格式）
       └─ 界面②：项目浏览器（Project → Well → Dataset → Variable）
```

用户要求把**前两个界面合并成一个** —— 启动后直接落在项目工作台里工作，
不再有任何前置对话框。

### 2.3.2 界面①的两项能力如何下沉

界面①并未被丢弃，它的每一项能力都在项目工作台里有了对应落点：

| 界面①原有能力 | 合并后的落点 |
|---|---|
| 选任务：quicklook / 综合解释 | **右键井** → 快速解释图 / 综合解释（项目级工具条另有批量） |
| 选井目录（原始资料目录） | **右键井** → 关联原始资料目录…（存 `project.json`，跨会话持久） |
| 校正测井 LAS（防止找错文件） | **右键井** → 指定主 LAS…（手工指定优先于自动探测） |
| 校正气测文件 | **右键井** → 指定气测文件… |
| 校正出图格式（甲方格式） | **右键井** → 选择甲方出图格式… |
| 「无井目录也能跑」的快捷通道 | 命令行通道保留：`python logInt.py <LAS>`、`--quicklook <目录>` |

合并后**界面上多了一个东西**：属性面板的「**资料**」页签，显式列出
"作业实际会用的文件"及其来源（手工指定 / 自动探测 / 未指定）——
这是界面①从来没有过的可见性。

### 2.3.3 合并后的入口层级

```
logInt 启动（无参数）
  └─ 项目工作台（唯一界面，根窗口，关闭即退出）
       ├─ 左侧：项目树 Project → Well → Dataset → Variable
       │    └─ 右键井 → 快速解释图 / 综合解释        ← 作业在这里
       │    └─ 右键井 → 指定主 LAS / 气测 / 出图格式 ← 资料校正在这里
       │    └─ 右键井 → 关联原始资料目录…
       ├─ 右侧：属性面板（概览 / 井信息 / 数据集 / 变量 / **资料** / 原始）
       ├─ 工具条：批量快速解释图 / 批量综合解释 / 源根管理
       └─ 底部：输出区（作业日志实时回传）
```

### 2.3.4 顺带解决的三件事

1. **依赖检查不再阻塞启动**。界面①之前会等一次 Enter（"按 Enter 键继续尝试运行"）。
   合并后主进程不再跑解释流程（解释都在子进程里），依赖检查改为**不等待**，
   启动即进工作台。脚本通道（`--quicklook` / 直传 LAS）仍保持等待行为。
2. **项目根有默认值**。工作台启动时直接用仓库 `output/` 作为项目根，
   不再弹目录选择框；不存在时才弹。
3. **界面命名统一为"项目工作台"**（原"项目浏览器"），因为它现在承载的不只是浏览。

## 二、Techlog 语义 → logInt 领域对象的逐项映射

映射依据是 Techlog 官方帮助的 16 个 Project 相关章节原文（从 MSI 内嵌 CAB 提取），
核心是 `Project browser / Common actions`、`Filter the project browser`、
`Techlog windows / Properties window`。

### 2.1 对象模型

| Techlog | 官方语义（摘自帮助） | logInt 落地 | 实现依据 |
|---|---|---|---|
| **Project** | 项目 = 多井容器；项目树根节点 | 项目根目录（默认 `D:\360\src\output`） | `scan_project()` |
| **Well** | 井 = 数据集与对象的归属 | 井目录 `output/<井名>/` | `scan_well()` |
| **Dataset** | 数据集 = 一组同类数据，**带类型图标** | 产物文件族（曲线集/层段表/成果LAS/图件/元信息） | `_DATASET_RULES` |
| **Variable** | 变量 = 曲线，**带 family 与 unit** | `processed.csv` 的列（71 列） | `_scan_variables_from_csv()` |

### 2.2 数据集类型 → Techlog 图标语义

Techlog 帮助 `Common actions` 用不同图标区分 9 种数据集类型。本系统收敛为 8 种：

| Techlog 图标语义 | 本系统数据集 | 典型文件 |
|---|---|---|
| 连续深度增量（continuous depth increment） | 解释曲线集 `curve` | `<井>_processed.csv` |
| 顶底深度边界（top-bottom depths） | 层段表 `table` | `<井>_interpretation_layers.csv` |
| 成果 LAS（点集/参考集） | 解释成果 `log` | `<井>_interpreted.LAS` |
| 图像类（Core/Borehole images） | 图件 `image` | `<井>_composite_log_*.pdf`、`_crossplot_*.pdf` |
| 点数据（point data set） | — | 由层段表派生 |
| PQC 集 / Quanti 集 / 多井图像集 | — | 本系统无对应，不虚构 |
| 接触面集（contact dataset） | — | 本系统无对应，不虚构 |

> **取舍说明**：Techlog 有 9 种数据集类型，本系统只实现有真实文件来源的 5 类。
> 没有数据支撑的类型**不做占位假实现**——宁可少一个图标，也不让用户点进去是空的。

### 2.3 变量三色规则（Techlog 最具辨识度的设计）

Techlog 帮助原文：

> "The name of the variable is in black: The log supports both a family and a unit.
>  The name of the variable is in gray: The log misses either a unit or a family.
>  The name of the variable is in red: The log misses both a family and a unit."

本系统**逐字复刻**该规则：

| 颜色 | 条件 | 本系统示例 |
|---|---|---|
| 黑（`ok`） | 族 + 单位齐备 | `GR`（自然伽马 / API）、`RT`（电阻率 / ohm.m） |
| 灰（`warn`） | 缺族或缺单位其一 | `LITHOLOGY`（岩性 / 无单位） |
| 红（`error`） | 族与单位皆缺 | `RHOB`（未登记族） |

实现见 `project_model.classify_variable()`，由 `ALL_FAMILIES` 族表驱动：

- **岩石物理族** 16 条（MD/GR/DEN/CNL/DT/RT/CAL/PE/SP/LLD/LLS/MSFL/PERM/TVD/AZIM/DEVI）
- **派生族** 17 条（POR/SW/So/Sg/PHI/VSH/VClay/VQuartz/VCalcite/VDolomite/RTI/NDI/GSI/CGI…）
- **解释族** 9 条（LITHOLOGY/LITH_MC_CONF/INTERPRETATION/FACIES/LAYER_ID/LAYER_LABEL/IS_CASING…）
- **井段工具族** 5 条（BS/CALS/DRHO/TENS/SPED/MTEM）
- **内部列** 12 个（`_POROSITY_VALID`/`SPRING_QC`/`VSH_PREV`/`INTERPRETATION_SCORE`…）→ 灰色圆点，不作为用户变量

> 族的划分直接复用了 logInt 既有的 `CURVE_NAME_ALIASES`（DEN/CNL/DT/RT/CAL/PE/GR 标准名）
> 与 `RESISTIVITY_CANDIDATES`，**不另立一套口径**，避免与解释流程的曲线名归一化脱节。

### 2.4 交互能力对照

## 三、架构与实现

### 3.1 分层

```
logInt.py  (入口分发)
   ├─ --project [root]           → 启动项目浏览器
   ├─ --quicklook <井目录>        → 单井快速解释（脚本/批处理通道，保留）
   └─ 启动界面「项目」(默认第一项) → 启动项目浏览器
                    │
                    ▼
logsys/project_browser.py   ← GUI 层（tkinter）：树 / 属性面板 / 输出区 / 项目作业
   │  只做展示与交互，不含业务规则
   ├──────────────────► logsys/project_job.py   ← 作业执行器（子进程跑 logInt）
   │                       └─ 实时日志回传 Output window
   ▼
logsys/project_model.py     ← 模型层（纯逻辑）：扫描 / 分类 / 过滤 / 分组 / 选择
   │  无 tkinter 依赖，可独立单测
   ▼
logsys/project_config.py    ← 配置层（纯逻辑）：井 ↔ 原始资料目录 绑定（project.json）
   │
   ▼
文件系统（D:\360\src\output\<井名>\  +  原始资料目录）
```

**为什么拆三层**：沿用 logsys 包的既有约定——"每个子模块可独立运行、可单测
（不依赖 GUI）"。模型层与配置层 87 项自检全部无需 GUI；作业执行器独立于
GUI，便于命令行复现（`python -m logsys.project_job --well BET-1 --job quicklook`）。

### 3.2 模型层 API

```python
scan_project(root, source_root='', source_map=None)  -> Project  # 扫描项目
scan_well(well_dir, source_dir='')                  -> Well      # 扫描单井
filter_wells(project, text, dataset_type, variable, status) -> [Well]
group_wells(wells, key)             -> {组名: [Well]}   # key: status/country/field
conditional_select(project, family, unit, kind) -> {井: {数据集: [变量]}}
summarize(project)                  -> 统计 dict
classify_variable(col)              -> 族/单位/三色
```

### 3.2b 配置层 API

```python
load_config(root) / save_config(root, cfg)      # project.json 读写（原子写）
bind_well(root, well, source_dir)               # 显式绑定井 → 源目录（保留既有资料指定）
unbind_well(root, well)
add_source_root(root, dir) / remove_source_root(root, dir)
detect_source_dir(well, roots)                  # 四级自动探测
resolve_source_dir(root, well)                  # 绑定 > 探测
source_map(root, well_names)                    # 批量解析

# —— 第三轮新增：井级资料指定（原启动界面的资料校正能力下沉）——
set_well_option(root, well, key, value)         # key ∈ las / gas / config
well_options(root, well)                        # 读取三项指定
clear_well_options(root, well)                  # 清除三项（保留源目录绑定）

# —— 第三轮新增：路径卫生 ——
normalize_source_root(path)                     # 修复 ":\<数字>" 片段被吞的损坏
invalid_source_roots(root)                      # 诊断不存在的源根
repair_source_roots(root)                       # 修复损坏源根 + 清理空壳条目
```

### 3.2c 作业层 API

```python
python_exe()                       # 优先项目 .venv 解释器
build_command(job_type, ...)       # → [py, logInt.py, --quicklook, <井目录>, ...]
find_main_las(well_dir)            # 主 LAS 发现（排除气测 LAS）
find_client_format(well_dir)       # 甲方出图格式发现
JobRunner(on_log, on_done).start(job_type, source_dir, project_root)
```

### 3.3 井状态判定（两个正交维度）

| 产物完成度 `status` | 判据 | 图标 | 含义 |
|---|---|---|---|
| `complete` 已解释 | 有曲线集 **且**（有成果LAS 或 有层段表） | ✓ | 解释产物齐备 |
| `partial` 部分完成 | 有曲线集或成果LAS，但缺另一半 | ◐ | 需重跑 |
| `pending` 待解释 | 源资料已就位，尚无产物 | ◔ | **可在项目里做作业的井** |
| `empty` 仅建目录 | 什么都没有 | ○ | 空壳 |

| 源关联 `has_source` | 判据 | 标记 | 含义 |
|---|---|---|---|
| 已关联 | 绑定了有效原始资料目录 | — | 可跑 QuickLook / 综合解释 |
| 缺源 | 未绑定 | ⚠ | 有产物但无法重跑/复核 |

### 3.4 性能

- 扫描 18 口井 / 73 数据集 / 1,154 变量：**< 2 秒**
- 变量提取只读 CSV 表头 + 前 200 行，**不整表载入**（processed.csv 单个可达 15 MB）
- 深度范围用首列流式扫描，不构造 DataFrame
- 过滤防抖 250ms，避免逐字符全量重扫
